# restricted-russian-ca

Многим российским сайтам нужен сертификат минцифры (НУЦ):
https://www.gosuslugi.ru/landing/crt

Проблема: сертификат не ограничен по списку доменов. Установивший его
доверяет подписи любого контента держателем ключа — зона действия
фактически не ограничена.

Цель: дать пользователю возможность доверять сертификату минцифры только
для явно заданного списка доменов.

## Принцип работы (name-constrained proxy)

Приватный ключ минцифры недоступен, поэтому «перевыпустить их сертификат
с ограничениями» нельзя. Вместо этого:

1. Пользователь генерирует свой личный root CA — максимально ограниченный:
   - `nameConstraints` (критическое): permittedSubtrees = DNS-имена из
     списка доменов; excludedSubtrees = IP `0.0.0.0/0` и `::/0`
     (защита от обхода через IP SAN)
   - `pathLenConstraint: 2` — ровно `root → proxy → subCA → leaf`
   - `keyUsage: keyCertSign, cRLSign` (critical)
   - срок действия: по умолчанию бессрочный (`99991231235959Z`),
     опционально ограничивается полем на странице
   - на root НЕ ставим directoryName-constraints: DN-констрейнт применяется
     ко всем сертам ниже, включая leaf с произвольным subject, и сломал бы
     валидацию легитимных сайтов (подтверждено в POC)
2. Собирается proxy-сертификат: subject и публичный ключ копируются из
   оригинального рута минцифры, issuer — личный root пользователя,
   `nameConstraints` идентичные root, `pathLenConstraint: 1`,
   SKI = hash публичного ключа (= SKI оригинального рута).
3. В систему ставятся только личный root + proxy. Оригинальный рут
   минцифры никогда не устанавливается.
4. Цепочка на устройстве: leaf → Russian Trusted Sub CA (прислан сайтом)
   → proxy (локальный intermediate; подпись минцифры сходится с его
   публичным ключом) → личный root (trust anchor). Домены вне списка
   отбрасываются проверкой name constraints (RFC 5280).

Принято: NC идентичны и на root, и на proxy (DNS permitted + IP excluded).
На root NC оставляем как бесплатное усиление для клиентов, применяющих
constraints из anchor (RFC 5280 делает это опциональным; OpenSSL 3.5
проверено — игнорирует anchor-NC), поэтому **гарантированная линия
обороны — NC на proxy** (intermediate-констрейнты применяются всеми
клиентами всегда). Запинить конкретный SPKI потомка в X.509 невозможно,
поэтому потолок вора украденного ключа root — выпуск leaf-сертификатов
только для доменов из списка.

Изменение списка доменов → перевыпуск root-сертификата (тем же ключом:
root.pem пользователя не устаревает как ключ, обновляется cert-часть) +
новый proxy → переустановка обоих. Если загруженный на страницу root уже
покрывает новый список своим NC → перегенерируется только proxy.

Хранение root между генерациями — ответственность пользователя.

## Интерфейс: статическая браузерная страница

Единственный интерфейс генерации — `docs/index.html` (GitHub Pages,
одностраничник, всё инлайн, работает офлайн; pkijs + WebCrypto):

- Единая форма: textarea с доменами (предзаполнена из
  `allowed-domains.txt`) + необязательный file-picker для root +
  необязательное поле срока действия (дней; пусто = бессрочно).
- Файл не указан → генерируется новый root (WebCrypto, ECDSA P-256),
  скачиваются `root.pem` (ключ + сертификат в одном PEM) и `proxy.crt`.
- Файл указан → root валидируется (`CA:TRUE`, показ SHA256 fingerprint)
  и используется; скачивается только `proxy.crt`. Если NC загруженного
  root не покрывает новый список доменов → root-сертификат перевыпускается
  на том же ключе (скачиваются обновлённый `root.pem` + `proxy.crt`).
- Страница stateless: приватный ключ живёт только в памяти вкладки,
  никакого localStorage.
- Самопроверка собранной цепочки прямо на странице.
- Пиннинг: SHA256 рута минцифры из `pinned-fingerprints.json` проверяется
  при каждой генерации; эталонная копия рута обновляется через PR.

## Состав репозитория

```
allowed-domains.txt        дефолтный список доменов (IDN → punycode)
pinned/mincifry-root.crt   эталонная копия рута минцифры
pinned/mincifry-sub-ca.crt эталонная копия subCA (для self-тестов)
pinned-fingerprints.json   SHA256 + независимые источники для drift-check
docs/index.html            генератор (single-file, RU-интерфейс)
scripts/generate.py        референсная реализация (Python 3 stdlib +
                           OpenSSL CLI, без pip-зависимостей)
scripts/verify.py          self-tests: тест-иерархия + реальная цепочка +
                           E2E на живые сайты (--e2e)
.github/workflows/ci.yml   проверки (без релизов)
README.md                  принцип, threat model, установка по ОС, FAQ
```

## CI (только проверки, релизов нет)

- PR/push: валидация синтаксиса `allowed-domains.txt` + self-tests
  (тест-иерархия: разрешённый домен проходит; посторонний, no-SAN и
  IP-SAN leaf отбрасываются).
- Weekly: drift-check SHA256 рута минцифры по официальному источнику
  (изменился → issue) + E2E на живые сайты через `openssl s_client`.
- Деплой GitHub Pages.

## Установка (в README, copy-paste командами, без скриптов)

- Linux: `update-ca-certificates`
- Windows: `certutil -addstore`
- macOS: `security add-trusted-cert`
- Firefox: `policies.json` (`certificates.Install`)

Сертификаты портабельны: одни и те же файлы ставятся на все устройства;
приватный ключ покидает устройство только если пользователь сам перенесёт
`root.pem`.

## Принятые решения

- NC на root и proxy (идентичные); root по умолчанию бессрочный, срок
  опционален полем на странице; при изменении доменов root-сертификат
  перевыпускается тем же ключом.
- Синтаксис IP-исключений в openssl-конфиге — address/netmask
  (`0.0.0.0/0.0.0.0`), CIDR-форма не парсится.
- От CI-релизов репозитория отказались: браузерная страница полностью
  закрывает генерацию.
- Отложено/выкинуто: транспорт через file.io/tmpfiles, fork-режим,
  composite action, установочные скрипты, localStorage.
- Секретов в проекте нет: единственный приватный ключ принадлежит
  пользователю и не покидает его браузер/устройство.

## Порядок реализации

1. POC: снять живую цепочку минцифры (структура root → subCA → leaf,
   реальная глубина → pathlen), запинить; проверить name constraints
   на тест-иерархии (`openssl verify`); проверить применение anchor-NC
   (nameConstraints в trust anchor) по платформам: OpenSSL,
   NSS/Firefox, Windows, macOS; найти официальный URL рута для
   drift-check; проверить pkijs + WebCrypto (сборка и подпись
   nameConstraints).
2. `scripts/generate.py` + `scripts/verify.py` + тесты.
3. CI-workflows.
4. `docs/index.html`.
5. README (RU).
6. Ручная матрица платформ (Linux/Firefox+Chrome, Windows, macOS):
   принимает ли каждая цепочку через локальный intermediate
   (включая AIA-казусы).
